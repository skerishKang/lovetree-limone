## 3. Promise.all barrier + UNIQUE retry 진위 확인

**테스트 구조 (`two different clientKeys created concurrently...`):**
1. **barrier (`armSortOrderBarrier(2)`)**: fake DB의 `then()`에서 `select({ sortOrder })` 형태의 sortOrder 계산 SELECT가 두 요청 모두 같은 MAX(sortOrder)를 읽을 때까지 resolve를 보류 → **두 요청이 동일한 `nextSortOrder`를 관측하도록 인위적으로 경합을 강제**.
2. **실제 UNIQUE 검사**: fake insert가 `(tree_id, sort_order)` 충돌을 실제 `find`로 검사해 `memories_tree_sort_order_uniq` duplicate 에러를 reject → 실 DB UNIQUE 인덱스 동작을 모사.
3. **retry 경로 강제·검증**: 두 번째 요청은 충돌을 만나 `insertMemoryWithRetry` 루프(SORT_ORDER_MAX_RETRIES=5)에서 재시도 → 최신 MAX를 다시 읽어 연속 sortOrder 확보.
4. **단언**: 둘 다 201, ID 상이, sortOrder 상이·연속(0,1), 정확히 2행 저장, 두 clientKey 모두 저장, **`getUniqueCollisionCount() >= 1`** 로 실제 충돌·retry 실행을 증명.

**판정**: 단순 mock 우연이 아닌, barrier로 경합을 강제하고 실제 UNIQUE 충돌 검사로 retry 경로가 반드시 실행됨을 검증하는 **진정한 동시성 테스트**. UNIQUE+retry 설계의 핵심 시나리오를 실제로 커버. (업데이트된 스테일 테스트 3건도 `inserted[0].value.sortOrder===0`으로 서버 권위를 실질 검증.)
