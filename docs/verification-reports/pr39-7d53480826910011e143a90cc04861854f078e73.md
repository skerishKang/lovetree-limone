## 3. 정적 코드 검토 (PR #39 head `7d53480`)

### 3.1 결함 (FINDINGS)

**F1 — `(tree_id, sort_order)`에 UNIQUE 제약 없음 (데이터 무결성 격차)**
- `db/schema.ts` / 마이그레이션: `memories_tree_sort_order_idx`는 **비유니크 인덱스** (`0002_snapshot.json` `isUnique=false`).
- `createMemory`/`createTreeMemory`는 `SELECT MAX(sortOrder)+1`을 단일 쿼리로 계산 후 insert.
- 동일 트리에 대한 동시 append 시 두 요청이 같은 MAX를 읽어 **중복 sortOrder가 DB 수준에서 막히지 않고 저장**될 수 있음 (정렬 무결성 저하, 데이터 유실은 아님).
- 대조: `memories_tree_client_key_uniq`, `trees_owner_client_key_uniq`는 UNIQUE=True. 즉 clientKey 중복은 DB가 막지만 **sortOrder 중복은 막지 않음**.

**F2 — retry / 409 충돌 처리 없음**
- insert 지점(`server/api/memories.ts:211`, `:356`)에 `try/catch`, 재시도, 409 응답 전부 없음.
- 동시 same-clientKey 요청: 두 요청이 선조회를 통과한 뒤 모두 insert → 둘째 insert가 `memories_tree_client_key_uniq` 위반으로 **unhandled exception → 500** (409 반환·재시도 없음).
- 설계 의도(BLOCKER_NOTES 및 컴2 브랜치 WIP)인 "unique index + bounded retry + 409"가 **head에는 미반영**.

**F3 — `trees.ts:22` `MAX_SAFE_SORT_ORDER = 0` (메모리 생성과 불일치)**
- `server/api/trees.ts`의 `MAX_SAFE_SORT_ORDER = 0`인 반면 `server/api/memories.ts`는 `10_000_000`.
- `createTreeWithFirstMemory`의 메모리 검증에서 sortOrder `max: 0` → 클라이언트가 첫 메모리에 `sortOrder > 0` 전송 시 **400 거부**.
- 현재 서버가 첫 메모리 `sortOrder: 0`을 강제하므로 정상 흐름은 통과하나, 상수 불일치이며 BLOCKER_NOTES의 "sortOrder가 create 검증에서 제거됨"이라는 기술과도 실제 코드 상태(`sortOrder`가 create 규칙에 잔존, `max 0`/`max 10M`)가 불일치.

- **clientKey 선조회**: `createMemory`, `createTreeMemory` 모두 `if (clientKey) { select where treeId+clientKey → 기존 반환 }` 존재.

## 4. 테스트 진위 검토 (PR #39 head의 신규 `tests/moment-data-spine.test.mjs`)

**한계 (T1–T5, 모두 비차단):**

- **T1 동시성 테스트 없음**: 테스트 파일 내 `Promise.all`은 mock의 `batch` 헬퍼(비사용)에만 존재. F1/F2의 동시 append·unique 충돌 시나리오는 **전혀 테스트되지 않음**.
- **T2 mock DB가 `where` 조건을 실제 필터링하지 않음**: `where()`는 조건만 저장하고 `_resolve()`는 시드된 fixture를 조건과 무관하게 `shift()`로 반환. 질의 필터 버그를 잡아낼 수 없음.
- **T3 mock DB가 unique 제약/insert 오류를 모사하지 않음**: insert가 항상 성공. retry/409 경로(F2)는 아예 테스트 불가.
- **T4 "API and selector sorting produce identical results" 명칭 과장**: 실제로는 `sortMoments()` **셀렉터만 호출**하며 GET API를 호출하지 않음. 또한 mock `orderBy`가 정렬을 수행하지 않아 GET으로 조회해도 DB 정렬을 검증하지 못함.
- **T5 "duplicate submission with same clientKey"는 요청 2회가 아님**: 라우터를 **1회** 호출하되, 두 개의 시드 fixture(`memoryRows: [[existing],[existing]]`)를 라우터 내부의 두 질의(MAX-sortOrder 질의 + clientKey 선조회 질의)가 각각 소비하는 방식으로 선조회 short-circuit 경로만 검증. 진짜 동일 요청 2회에 대한 HTTP/DB 상태 레벨 멱등성은 검증하지 못함.

**양호한 점**: 49개 백엔드 테스트가 실제 라우터 진입·검증·권한 경로를 통과하며, 핵심 happy-path 동작과 정렬 계약을 커버.
